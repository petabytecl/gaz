## Architecture Patterns

### System Architecture: Lock-During-Blocking-IO Fix Pattern

All three concurrency fixes (EventBus, cron, DI singleton) follow the same structural pattern:

```
CURRENT (buggy):
  Lock() -> blocking operation -> Unlock()

FIXED:
  Lock() -> snapshot state -> Unlock() -> blocking operation on snapshot
```

### Pattern 1: Snapshot-Under-Lock (EventBus Publish)
**What:** Copy handler slice under RLock, release lock, iterate and send outside lock.
**When to use:** Any code that holds a read lock while sending on channels or performing I/O.
**Current code (buggy):** [VERIFIED: eventbus/bus.go:154-191]

```go
// CURRENT: bus.go:154-191 -- holds RLock across channel sends
func Publish[T Event](ctx context.Context, b *EventBus, event T, topic string) {
    b.mu.RLock()
    if b.closed {
        b.mu.RUnlock()
        return
    }
    // ... collect handlers ...
    // Deliver while holding RLock -- RULE 1 VIOLATION
    for _, h := range handlers {
        select {
        case h.ch <- env:  // blocks if buffer full, while holding lock
        case <-ctx.Done():
            b.mu.RUnlock()
            return
        }
    }
    b.mu.RUnlock()
}
```

**Fixed pattern:**
```go
func Publish[T Event](ctx context.Context, b *EventBus, event T, topic string) {
    b.mu.RLock()
    if b.closed {
        b.mu.RUnlock()
        return
    }
    // Snapshot handlers under lock
    handlers := snapshotHandlers(b, eventType, topic)
    b.mu.RUnlock()
    
    // Deliver outside lock -- no deadlock possible
    env := eventEnvelope{ctx: ctx, event: event}
    for _, h := range handlers {
        select {
        case h.ch <- env:
        case <-h.tombstone:  // subscription cancelled during send
        case <-ctx.Done():
            return
        }
    }
}
```

**Tombstone mechanism:** Each `asyncSubscription` gets a new `tombstone chan struct{}` field. `Close()` sets the tombstone before closing `ch` so post-snapshot senders can short-circuit. This replaces the "channels closed under write lock" safety guarantee with a per-subscription signal. [VERIFIED: approach from CONTEXT.md item 2]

### Pattern 2: Snapshot-Under-Lock (Cron Schedule/Entries/Remove/Stop)
**What:** Read `c.running` under `runningMu`, release lock, then channel-send outside lock.
**When to use:** All four public methods that send on internal channels.
**Current code (buggy):** [VERIFIED: cron/internal/cron.go:136-148, 155-161, 181-188, 302-308]

```go
// CURRENT: All four methods hold runningMu across channel send/recv
func (c *Cron) Schedule(schedule Schedule, cmd Job) EntryID {
    c.runningMu.Lock()
    defer c.runningMu.Unlock()  // held during c.add <- entry
    // ...
    if c.running {
        c.add <- entry  // BLOCKS while holding mutex
    }
    // ...
}
```

**Fixed pattern:**
```go
func (c *Cron) Schedule(schedule Schedule, cmd Job) EntryID {
    c.runningMu.Lock()
    running := c.running
    // ... prepare entry ...
    if !running {
        c.entries = append(c.entries, entry)
        c.runningMu.Unlock()
        return entry.ID
    }
    c.runningMu.Unlock()
    
    // Channel send outside lock with safety valve
    select {
    case c.add <- entry:
    case <-c.stop:
        // Scheduler exited -- no-op
    }
    return entry.ID
}
```

Apply uniformly to `Entries()`, `Remove()`, and `Stop()`. [VERIFIED: approach from CONTEXT.md item 3]

### Pattern 3: sync.Once + Atomic for DI Singleton
**What:** Replace mu+built pattern with sync.Once for one-shot initialization, atomic.Pointer for the cached instance.
**When to use:** Singleton initialization that must be safe for both concurrent and re-entrant access.
**Current code (buggy):** [VERIFIED: di/service.go:151-172, 297-318]

```go
// CURRENT: holds mu while running provider (which may do I/O or re-enter)
func (s *lazySingleton[T]) GetInstance(c *Container, chain []string) (any, error) {
    s.mu.Lock()
    defer s.mu.Unlock()
    if s.built {
        return s.instance, nil
    }
    instance, err := s.provider(c)  // BLOCKS under lock -- Rule 1 violation
    // ...
}
```

**Fixed pattern -- using sync.Once:**
```go
type lazySingleton[T any] struct {
    baseService
    provider func(*Container) (T, error)
    
    once     sync.Once
    instance T
    err      error
    built    atomic.Bool
    
    initGoid int64  // goroutine ID of initializer, for re-entrant cycle detection
}

func (s *lazySingleton[T]) GetInstance(c *Container, chain []string) (any, error) {
    if s.built.Load() {
        return s.instance, nil
    }
    
    s.once.Do(func() {
        // Record initializing goroutine for re-entrant cycle detection
        goid := currentGoroutineID()
        s.initGoid = goid
        
        instance, err := s.provider(c)
        if err != nil {
            s.err = err
            return
        }
        if injectErr := injectStruct(c, instance, chain); injectErr != nil {
            s.err = injectErr
            return
        }
        s.instance = instance
        s.built.Store(true)
    })
    
    return s.instance, s.err
}
```

**Critical consideration for Start/Stop:** The `Start()` and `Stop()` methods also hold `s.mu` while calling user lifecycle hooks (OnStart/OnStop). These need the same treatment -- check `s.built` via atomic load, then call hooks without holding any lock. Since `Start()` and `Stop()` are called sequentially from the lifecycle engine (after Build completes), there is no concurrent access concern for the instance field once built. [VERIFIED: di/service.go:174-194, 320-341]

**Re-entrant cycle detection:** The current per-goroutine cycle detection via `goid` (in container.go) catches same-goroutine cycles during `Resolve`. The new fix must also detect when a `sync.Once` initializer tries to resolve the same singleton from the same goroutine -- this would deadlock on `Once.Do`. Store the initializing goroutine ID and fail fast with `ErrCycle` if re-entered. [VERIFIED: approach from CONTEXT.md item 6]

### Pattern 4: Cobra Single Startup Path
**What:** Extract a shared `startServices(ctx)` method from `app_run.go:Run()` that both `Run()` and `cobra.bootstrap()` call.
**Current code (buggy):** [VERIFIED: cobra.go:179-214]

The `Start()` method in `cobra.go` re-implements lifecycle inline:
- Does NOT filter workers (workers get started by both DI layer AND workerMgr -- double start)
- Does NOT use parallel layer startup (sequential only)
- Does NOT have panic recovery
- Does NOT have rollback on failure
- Does NOT start the worker manager at all (workers are never supervised)

**Diff between Run() and Start():**

| Feature | Run() (app_run.go) | Start() (cobra.go) |
|---------|-------------------|-------------------|
| Worker filtering | YES (collectNonWorkerServices pattern) | NO |
| Parallel layer startup | YES (goroutine per service in layer) | NO (sequential) |
| Panic recovery | YES (via goroutine error handling) | NO |
| Error rollback | YES (Stop on failure) | NO |
| Worker manager start | YES (a.workerMgr.Start) | NO |
| ShutdownTimeout respect | YES | NO |

**Fix:** Extract the Run() service startup logic (lines 39-118 in app_run.go) into a private `startServices(ctx context.Context) error` method. Both `Run()` and `cobra.bootstrap()` call it. The `Start()` method in cobra.go should be either removed or refactored to delegate to `startServices()`.

The worker filter helper `collectNonWorkerServices()` should be extracted from the inline lambda in `Run()` and shared. [VERIFIED: approach from CONTEXT.md item 1]

### Anti-Patterns to Avoid
- **Lock-during-blocking-IO (Rule 1):** Never hold a mutex while sending on a channel, waiting on a WaitGroup, performing network I/O, or waiting on a context. This is the root cause of items 2, 3, and 6.
- **Duplicated lifecycle paths (Rule 2):** Never re-implement startup/shutdown logic in a new entry point. Always delegate to a shared method.
- **Insecure-by-default config (Rule 7):** Security-sensitive features must default to the restrictive option. Reflection exposes the full API schema.
- **Mutable CI tags (Rule 8):** Always pin GitHub Actions to full SHA digests.

## Common Pitfalls

### Pitfall 1: Send-on-Closed-Channel After Lock Release
**What goes wrong:** After releasing the lock, another goroutine closes the channel before the send completes, causing a panic.
**Why it happens:** The "channels closed under write lock" invariant is broken when Publish releases the lock before sending.
**How to avoid:** Use a per-subscription tombstone channel. `Close()` sets tombstone before closing `ch`. Senders use `select { case h.ch <- env: case <-h.tombstone: }` to detect closed subscriptions.
**Warning signs:** Panic in `Publish` during concurrent `Close()` calls.

### Pitfall 2: sync.Once Swallows Provider Errors
**What goes wrong:** `sync.Once.Do` runs the function exactly once. If the provider fails, subsequent calls see `once` as "done" but the instance is nil.
**Why it happens:** `sync.Once` does not distinguish between success and failure.
**How to avoid:** Cache both the instance and the error in the `Once.Do` closure. Callers check the error field after `once.Do` returns.
**Warning signs:** Nil pointer dereference after a provider failure.

### Pitfall 3: Cron Stop() Deadlock After Scheduler Exit
**What goes wrong:** If the scheduler goroutine has already exited (e.g., due to a panic), `Stop()` sends on `c.stop` which blocks forever because nobody is reading.
**Why it happens:** The current code does `c.stop <- struct{}{}` under lock.
**How to avoid:** Use `select { case c.stop <- struct{}{}: default: }` or better, close the stop channel instead of sending on it. But since the original robfig/cron design uses send-on-channel, the safer fix is the select-with-stop pattern shown in Pattern 2.
**Warning signs:** Test hangs during teardown.

### Pitfall 4: Reflection Default Flip Breaks Downstream Tests
**What goes wrong:** Tests that call `DefaultConfig()` and then assert `Reflection == true` will break.
**Why it happens:** Changing a default value is a behavioral break.
**How to avoid:** Update all test assertions that depend on the old default. Identified sites:
- `server/vanguard/config_test.go:28` -- `s.True(cfg.Reflection)` must become `s.False(cfg.Reflection)`
- `server/vanguard/module_test.go:43` -- `s.True(cfg.Reflection)` must become `s.False(cfg.Reflection)`
- No grpc config_test.go file exists (no assertion to update).
- Doc comment in `server/grpc/config.go:28` says "Defaults to true" -- must update.
- Doc comment in `server/vanguard/config.go:52` says "Defaults to true" -- must update.
**Warning signs:** Test failures in `make test` after the default change.

### Pitfall 5: DI Singleton Start/Stop Also Hold Lock During User Code
**What goes wrong:** Fix only `GetInstance` but forget that `Start()` and `Stop()` also hold `s.mu` while calling `runStartLifecycle` / `runStopLifecycle`, which execute user-provided OnStart/OnStop hooks.
**Why it happens:** The same mu+built pattern is used in Start/Stop.
**How to avoid:** Fix Start/Stop at the same time as GetInstance. Since Start/Stop are called sequentially by the lifecycle engine after Build, an atomic check of `built` is sufficient without a mutex.
**Warning signs:** Deadlock during shutdown when a service's OnStop calls back into the container.
