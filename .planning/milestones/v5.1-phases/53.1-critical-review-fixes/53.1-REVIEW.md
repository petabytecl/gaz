## Summary

Phase 53.1 fixed 6 critical findings: Cobra startup path divergence, EventBus lock-during-blocking-IO, Cron lock-during-channel-ops, DI singleton init-under-lock, gRPC reflection defaults, and GitHub Actions SHA pinning.

The DI singleton `sync.Once` pattern (di/service.go), the EventBus tombstone pattern (eventbus/bus.go), the GitHub Actions SHA pinning (.github/workflows/ci.yml), and the gRPC reflection defaults (server/grpc/config.go, server/vanguard/config.go) are correctly implemented.

However, two critical issues remain: the `handleSignalShutdown` has a race where two goroutines compete to consume from a buffered channel (causing a potential hang), and the cron `Scheduler.OnStop` still blocks on channel send + context wait while holding a mutex (violating Rule 1). Additionally, the EventBus `OnStop` ignores its context parameter, violating Rule 3.

## Critical Issues

### CR-01: handleSignalShutdown double-consume from shutdownDone channel

**File:** `app_run.go:178-200`
**Issue:** The `shutdownDone` channel has buffer size 1. Two goroutines compete to read from it: the force-exit watcher goroutine (line 193: `case <-shutdownDone:`) and the main goroutine (line 200: `return <-shutdownDone`). When shutdown completes before a second signal arrives, Go's scheduler may select the watcher's `case <-shutdownDone:` branch, consuming the only value. The main goroutine at line 200 then blocks forever, causing the application to hang instead of exiting cleanly.

This race is non-deterministic and depends on goroutine scheduling, making it difficult to reproduce in tests but likely to manifest under production load (especially when shutdown is fast).

**Fix:**
```go
// handleSignalShutdown handles graceful shutdown triggered by a signal.
func (a *App) handleSignalShutdown(
	ctx context.Context,
	sig os.Signal,
	sigCh <-chan os.Signal,
) error {
	a.Logger.InfoContext(ctx, "Shutting down gracefully...", "hint", "Ctrl+C again to force")

	shutdownCtx, cancel := context.WithTimeout(context.Background(), a.opts.ShutdownTimeout)
	defer cancel()

	// Channel to receive shutdown result
	shutdownDone := make(chan error, 1)

	go func() {
		shutdownDone <- a.Stop(shutdownCtx)
	}()

	// If SIGINT, spawn force-exit watcher goroutine
	if sig == os.Interrupt {
		go func() {
			select {
			case <-sigCh:
				a.Logger.ErrorContext(ctx, "Received second interrupt, forcing exit")
				callExitFunc(1)
			case <-shutdownCtx.Done():
				// Shutdown context completed (either Stop finished or timed out).
				// Watcher exits without consuming the channel value.
			}
		}()
	}

	// Only the main goroutine reads the result
	return <-shutdownDone
}
```

The fix replaces `case <-shutdownDone:` in the watcher with `case <-shutdownCtx.Done():`. The watcher now exits when the shutdown context completes (either Stop returned or the timeout fired), without consuming the channel value. Only the main goroutine at line 200 reads from `shutdownDone`.

### CR-02: Cron Scheduler.OnStop holds mutex during blocking channel send and context wait

**File:** `cron/scheduler.go:93-110`
**Issue:** `OnStop` acquires `s.mu.Lock()` (line 94, via `defer s.mu.Unlock()`) and then performs two blocking operations while holding it:
1. `s.cron.Stop()` (line 105) which internally sends on an unbuffered channel (`c.stop <- struct{}{}` at cron/internal/cron.go:341) -- this blocks until `run()` consumes the signal.
2. `<-cronCtx.Done()` (line 106) -- this blocks until all running jobs complete.

This directly violates Rule 1 (No Lock-During-Blocking-IO). If any other goroutine attempts to call `OnStart`, `RegisterJob`, or any method that acquires `s.mu`, it will deadlock for the entire duration of job draining.

**Fix:**
```go
func (s *Scheduler) OnStop(ctx context.Context) error {
	s.mu.Lock()
	if !s.running {
		s.mu.Unlock()
		return nil
	}
	s.running = false
	s.mu.Unlock() // Release lock BEFORE blocking operations

	s.logger.InfoContext(ctx, "stopping cron scheduler, waiting for running jobs")

	// Stop() sends on unbuffered channel (blocks until run() exits) then returns
	// a context that completes when all running jobs finish.
	cronCtx := s.cron.Stop()

	// Respect the shutdown context deadline (Rule 3)
	select {
	case <-cronCtx.Done():
		s.logger.InfoContext(ctx, "cron scheduler stopped")
		return nil
	case <-ctx.Done():
		s.logger.WarnContext(ctx, "cron shutdown deadline exceeded, abandoning job wait")
		return ctx.Err()
	}
}
```

### WR-01: EventBus.OnStop ignores shutdown context (Rule 3 violation)

**File:** `eventbus/bus.go:231-234`
**Issue:** `OnStop(_ context.Context)` discards the context parameter and calls `Close()`, which waits indefinitely for all handler goroutines to drain via `<-sub.done` (line 269). If a handler is slow or stuck, this blocks the entire shutdown pipeline until the global force-exit timer fires `os.Exit(1)`. This violates Rule 3 (Context Propagation in OnStop).

**Fix:**
```go
func (b *EventBus) OnStop(ctx context.Context) error {
	done := make(chan struct{})
	go func() {
		b.Close()
		close(done)
	}()

	select {
	case <-done:
		return nil
	case <-ctx.Done():
		b.logger.Warn("eventbus shutdown deadline exceeded, some handlers may not drain")
		return ctx.Err()
	}
}
```

### WR-02: Cron internal Stop() is not safe for concurrent calls

**File:** `cron/internal/cron.go:324-355`
**Issue:** If two goroutines call `Stop()` concurrently, both may see `c.running == true` (line 326) before either sends on `c.stop`. The first sender succeeds (run() consumes it and exits). The second sender blocks forever on `c.stop <- struct{}{}` (line 341) because `run()` has already returned and no goroutine reads from `c.stop`.

While the Scheduler wrapper (`cron/scheduler.go`) prevents this at the framework level via its own mutex, the internal `Cron.Stop()` method itself is documented as safe to call ("stops the cron scheduler if it is running") but is not safe for concurrent use. Any direct user of the internal package would hit this.

**Fix:**
```go
func (c *Cron) Stop() context.Context {
	c.runningMu.Lock()
	if !c.running {
		c.runningMu.Unlock()
		ctx, cancel := context.WithCancel(context.Background())
		go func() {
			c.jobWaiter.Wait()
			cancel()
		}()
		return ctx
	}
	c.running = false // Set false under lock BEFORE sending
	c.runningMu.Unlock()

	// Now send stop signal -- only one goroutine can reach here per Start() cycle
	c.stop <- struct{}{}

	ctx, cancel := context.WithCancel(context.Background())
	go func() {
		c.jobWaiter.Wait()
		cancel()
	}()
	return ctx
}
```

Setting `c.running = false` under the lock before releasing it ensures only one goroutine passes the guard and sends on the channel.

### WR-03: stopCh not initialized when Stop() called without Run() or bootstrap()

**File:** `app_shutdown.go:100-110`
**Issue:** In `doStop`, when `wasRunning` is true, the code checks `a.stopCh` to signal Run to exit. However, if `Stop()` is called externally (not from within Run/bootstrap) and `a.running` was set to true by `bootstrap()`, but then `waitForShutdownSignal` in the default RunE (cobra.go:74) has already read from `a.stopCh` and returned, the `select` at line 104 attempts to read from `a.stopCh` which may already be closed. The `case <-a.stopCh:` branch handles this correctly (detects already-closed), so this is safe. However, there's no nil guard on `a.stopCh` -- if `doStop` is called when `wasRunning` is somehow true but `a.stopCh` was never initialized (e.g., via a testing scenario that sets `a.running = true` directly), this panics.

This is unlikely in production but represents a defensive coding gap.

**Fix:** Add a nil guard:
```go
if wasRunning && a.stopCh != nil {
    a.mu.Lock()
    select {
    case <-a.stopCh:
    default:
        close(a.stopCh)
    }
    a.mu.Unlock()
}
```

### IN-01: Cron scheduler leaks goroutines on Stop when not running

**File:** `cron/internal/cron.go:328-334`
**Issue:** When `Stop()` is called and `c.running` is false, a new goroutine is spawned (line 330) to wait on `c.jobWaiter.Wait()`. If no jobs are pending, this goroutine completes immediately. But if jobs were started via a previous Start/Stop cycle, the `jobWaiter` counter may never reach zero if a job panicked without calling `Done()`. The goroutine would leak. The same pattern exists at line 349-353. This is a minor concern since job wrappers use `defer c.jobWaiter.Done()` (line 312), making panics safe.

**File:** `cron/internal/cron.go:329-333`
**Fix:** No action needed -- the `defer jobWaiter.Done()` in `startJob` ensures correctness. This is informational only.
