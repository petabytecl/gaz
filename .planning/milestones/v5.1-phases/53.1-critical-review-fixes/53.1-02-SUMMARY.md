# Phase 53.1 Plan 02: Cron + DI Lock-During-Blocking-IO Fixes Summary

Fix cron internal scheduler lock-during-channel-ops and DI singleton init-under-lock deadlock using snapshot-under-lock and sync.Once patterns (CLAUDE.md Rule 1).

## Task Commits

| Task | Name | Commit | Key Changes |
|------|------|--------|-------------|
| 1 | Fix cron scheduler lock-during-channel-ops | de8eeeb | Release runningMu before all channel ops; add done channel safety valve |
| 2 | Fix DI singleton GetInstance init-under-lock | cd54cc2 | Replace mu+built with sync.Once+atomic.Bool; add re-entrant cycle detection |

## Changes Made

### Cron Internal Scheduler (Task 1)

**Problem:** Schedule(), Entries(), Remove(), Stop() held `runningMu` during channel send/receive operations. If the scheduler goroutine stalled, every concurrent caller would deadlock.

**Solution:**
- All four methods now snapshot `c.running` under lock, release the lock, then perform channel operations outside the lock
- Added `done` channel (closed when `run()` exits) as safety valve for senders -- prevents stealing the stop signal meant for `run()`
- Stop() sets `running=false` AFTER `run()` has consumed the stop signal and returned, preventing a data race where another goroutine appends to `c.entries` while `run()` still reads them
- Stop() when not running still waits for `jobWaiter` (preserving original context completion semantics for outstanding jobs)
- Start() and Run() re-initialize the `done` channel to support stop-then-restart scenarios

**Files:** `cron/internal/cron.go`, `cron/internal/cron_test.go`

### DI Singleton Init (Task 2)

**Problem:** lazySingleton and eagerSingleton held `s.mu` during provider execution. If the provider did network I/O, held for the duration. If a different goroutine's dependency chain led back to the same singleton, deadlock. If the same goroutine re-entered, deadlock (goid-based detection was in the container, not in the service wrapper).

**Solution:**
- Replaced `sync.Mutex` + `bool` with `sync.Once` + `atomic.Bool` for initialization
- Fast path: `if s.built.Load()` returns cached instance without any synchronization
- `sync.Once.Do` ensures provider runs exactly once, even under concurrent access
- Added `initGoid atomic.Int64` field: stores goroutine ID during initialization, checked before `once.Do` to detect same-goroutine re-entrant resolution (fails fast with `ErrCycle`)
- Provider errors are cached: `sync.Once` semantics mean a failed provider is never retried
- Start/Stop are now lock-free: check `s.built.Load()` then call lifecycle hooks directly (safe because lifecycle engine calls them sequentially after Build)

**Files:** `di/service.go`, `di/service_test.go`

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Fixed c.stop channel consumption race in Entries/Schedule/Remove**
- **Found during:** Task 1
- **Issue:** Plan suggested using `case <-c.stop:` as safety valve in Schedule/Entries/Remove. This would consume the stop signal meant for run(), causing run() to never exit while Stop() returns thinking it succeeded.
- **Fix:** Added a separate `done` channel (closed by run() on exit) as the safety valve. Senders use `case <-c.done:` which is only signaled after run() has already exited.
- **Files modified:** cron/internal/cron.go
- **Commit:** de8eeeb

**2. [Rule 1 - Bug] Fixed Stop() data race on c.entries between run() and callers**
- **Found during:** Task 1
- **Issue:** Plan set `c.running = false` before sending on c.stop. Between setting running=false and run() actually exiting, another caller could see running=false and directly append to c.entries while run() still iterates them.
- **Fix:** Stop() sets running=false AFTER the stop signal is consumed (blocking send guarantees run() has exited).
- **Files modified:** cron/internal/cron.go
- **Commit:** de8eeeb

**3. [Rule 1 - Bug] Fixed Stop() context semantics when not running**
- **Found during:** Task 1
- **Issue:** Plan returned an immediately-cancelled context when not running. But outstanding jobs from a previous stop may still be running (the jobWaiter hasn't been waited on).
- **Fix:** When not running, still launch a goroutine that waits on jobWaiter before cancelling the context (matching original behavior).
- **Files modified:** cron/internal/cron.go
- **Commit:** de8eeeb
